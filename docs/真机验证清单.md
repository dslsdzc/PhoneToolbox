# 真机验证清单

> **这份清单本身没有被执行过** —— 本仓开发环境**无真机**（见 `README.md` 各条"真机未验证"）。
> 下面的步骤、判据与失败指纹，都是从**代码 + mock 通道级证据 + 上游源码**推出来的，**不是实测经验**。
> 它的用途是：**有设备时照着做一遍，把结果回填成证据**。

## 0. 怎么用

1. 按 §1 的顺序做：**先做便宜且能早期证伪的**（门控 → 传输层 → 利用链）。
2. 每步记 **§4 的字段**；失败时记**日志原文**（本工具所有关键路径都落日志，那是唯一能回溯的线索）。
3. **不要跳过"已知不确定点"那一栏** —— 那些是本仓**自己标出来的**薄弱处，最可能就是真机上出问题的地方。
4. 若某步失败且你判断是**本仓过严**（而设备其实正常），**记下来**：本仓有一批"有意从严"的裁决
  （见 §3），它们的前提是"没有真机证据时宁可假阴性"—— 真机数据正是用来推翻它们的东西。

## 1. 按顺序做

### 1.1 用户协议与风险分级门控（W2）—— 最便宜，先做这个

| | |
|---|---|
| **前置** | 无需设备。删掉 `~/.config/PhoneToolbox/*.ini`（或对应平台的用户配置） |
| **步骤** | ① 启动 → 应弹**使用须知**，未勾选时"接受"禁用；② 勾选并接受 → 进入主界面；③ **退出再启动** → 应**不再弹**；④ 进任一 Tier 2 功能（如解锁 BL）→ 应弹二次确认；拒绝 → **不发起任何动作**；接受一次后同一版本**不再弹**；⑤ 进任一 Tier 3 功能（如漏洞面板）→ 同样 |
| **判据** | ② 若不接受能进主界面 = **失败**；④ 拒绝后仍发起动作 = **失败** |
| **失败看什么** | `ConsentStore` 的键（ini 里的 `legal/agreementVersion`、`legal/tier2Version`、`legal/tier3Version`） |
| **已知不确定点** | **这条路径从未被自动化覆盖**（用例一律注入临时 store；生产 `store==nullptr` 分支按裁决不写用例）。另：门控是**客户端**的，删配置/改源码即可绕过 —— 它的价值在提醒与留痕，不在强制 |

### 1.2 W8-T1：USB 控制传输（整条利用链的地基）

| | |
|---|---|
| **前置** | 一台能进 **BROM 模式**的 MTK 设备（音量键组合或测试点） |
| **步骤** | 设备进 BROM 插 USB → 设备列表应认成 **MTK BROM / Preloader** → 打开漏洞面板 → 「解析载荷」→ 填 `hw_code` → 若状态行说"var1 缺失"，在覆盖框里填上游给的值 |
| **判据** | 设备被认出（VID/PID 白名单命中）；状态行给出**芯片表命中情况**（`dacode` / 代际 / kamakiri 三要素） |
| **失败看什么** | 若认不出：`mtkbrom::isKnownMtkUsbId` 的白名单（`mtk_brom.cpp` 的 `kUsbIds`）——**preloader 与 BROM 同一张表**，身份要**握手后**由 `GET_BL_VER`（0xFE）判定 |
| **已知不确定点** | `libusb_control_transfer` 的**时序与超时行为完全未验证**（T1 起就标注"无新行为可验"）；preloader 的**等待窗口比 BROM 短**，抢不抢得到是设备侧事实 |

### 1.3 W8 利用链（`runBromExploit`）—— 最能证伪整个特性的一步

| | |
|---|---|
| **前置** | 同上 + **载荷**（自备或按清单下载，sha256 必须通过）+ 一台**你确定可恢复**的设备 |
| **步骤** | 点「执行利用」→ 过 Tier 3 确认 → 看日志逐段 |
| **判据** | 日志出现"**触发序列已发完**"；**注意这句不等于保护位已关**（见下） |
| **失败看什么** | `ExploitResult::stage` 指出卡在哪一步；日志里"**目标设备：VID:PID … · usb-x-y**"那行是**唯一可信的"打到了哪台"记录**（`usb-<bus>-<addr>` **不是持久序列号**，重插会变） |
| **⚠️ 已知不确定点（三条，都是本仓自己标的）** | ① **保护位（SBC/SLA/DAA）是否真的关掉了，本层无法回读确认** —— `ok == true` 只代表触发序列发完了（I2 的裁决：不发明一个验证不了的检查）；② **priming 读失败即中止**（上游完全忽略这些读）—— 本仓**有意从严**，真机上可能**假阴性**；③ 已修补代际（V6）的判据是**粗判据**（纯静态表 `damode == Xml`，**不读设备**），会有**假阳性**；面板上的 opt-in 就是为它留的 |
| **两台同芯片设备** | 若你选了 A 但只插着 B（**同芯片**），操作的仍是 B —— 芯片码现场核对挡不住同型号。**只插一台再操作**是最稳的用法 |

### 1.4 W8-T5：preloader 安全修补

| | |
|---|---|
| **前置** | MTK 刷写流程里走到 preloader 那一步 |
| **步骤** | 在"是否对 preloader 打安全补丁"选**是** → 过 Tier 3 确认 → 刷写 |
| **判据** | 日志"preloader 安全修补：已改写 N 个字节模式 —— \<模式名\>"（**点名**）；未命中 → "**未命中任何已知模式**…这不是成功" |
| **⚠️ 作用范围（容易误解，务必看清）** | 修补**只作用于本次 EMI/DRAM 初始化用的内存副本**，**不改写设备上的 preloader 分区**（刷进去的是磁盘原文件）。要让设备带上修补版，**需自行落盘后刷入** |
| **已知不确定点** | XML 代际**不使用** preloader 字节 ⇒ 面板会**跳过并如实说明**（不是失败）。5 个字节模式来自 GPLv3 子模块；**真机上是否真被改写未验证** |

### 1.5 W8-T4：DA 切分另存

| | |
|---|---|
| **前置** | 一个真实的 `MTK_AllInOne_DA_*.bin`（**不需要设备**）+ 目标芯片的 `hw_code` |
| **步骤** | 刷机面板「导出 DA 片段…」→ 选 DA 文件 + 填 hw_code + 选输出目录 |
| **判据** | 生成 `da1.bin` / `da2.bin`；**da2 保留尾部签名**（LEGACY 不裁剪）；失败**不留半份产物** |
| **已知不确定点** | 若你的设备拿不到 `hw_code`（进不了 BROM），这一步就选不出条目 —— 这是**有意**的（`selectDaEntry` 需要 dacode，本仓**不许**按序号猜条目）。真样本已验证解析与切片逐字节正确；**真机 DA 未验** |

### 1.6 W8-T6 的 UI 分支（无自动化覆盖的那部分）

需要手点一遍：① **三个文件对话框**（选载荷 / 选 DA / 选输出目录）取消与错误路径；
② **网络获取载荷**（默认关）——开启后按本机清单下载并校验；③ **载荷 sha256 不过** → 按钮应**禁用 + 给出原因**（不是静默失败）。
判据：**sha256 只保证"与清单一致"，不保证载荷内容安全**（面板上写了这句，别当成安全属性）。

## 2. 一条设备能测到哪一步？

从"最省事"到"最能证伪"：
**门控（无需设备）→ 检测/识别 → DA 导出（无需设备，只要 DA 文件）→ 传输层握手 → 利用链触发 → 刷写。**

## 3. 本仓"有意从严"的裁决（真机上遇到假阴性时看这里）

这几处是**在没有真机证据时选择"宁可假阴性"**的结果 —— 真机数据正是推翻它们的东西，**别当成 bug 直接改**：

| 处 | 从严的做法 | 上游怎么做的 | 若真机假阴性怎么办 |
|---|---|---|---|
| priming 读（`mtk_brom_exploit.cpp`） | **读失败即中止** | 完全忽略这些读的结果 | 记下来 → 建议放宽为"记日志继续"，但需真机数据支撑 |
| 已修补代际判据 | **默认早退**（粗判据：静态表 `damode == Xml`） | 靠 `SEND_DA`/`JUMP_DA` 失败传播 | 面板上有 opt-in 可越过 |
| 芯片表缺字段 | **拒绝执行**（不填 0 兜底） | 表里就是 `None` | 若你的芯片在表里但缺 watchdog/uart ⇒ 该芯片本特性**不可用**（89 条里 23 条如此，是上游数据事实） |
| 载荷 sha256 | **fail-closed**（不过就不给执行） | — | 清单是我方维护的；若你的自备载荷不在清单里，走**手动导入** |

## 4. 每步要记的字段（回填成证据）

| 字段 | 为什么要 |
|---|---|
| 日期 / 机型 / 市场名 | 结果绑定机型 |
| `hw_code`（设备自报） | 芯片表的键；也是"打到哪台"的核对依据 |
| 固件版本 / patch 级别 | 已修补代际的判据 |
| 该步**通过 / 失败** | 判据见 §1 各行 |
| **日志原文**（整段，别摘要） | 失败时唯一能回溯的线索 |
| 若失败：是"本仓过严"还是"设备不支持" | 决定要不要放宽 §3 的从严裁决 |

## 5. 不要做的事

- **不要**在一台**不可恢复**的设备上跑利用链（它是在 BROM 上下文跑载荷，本仓**无真机证据**）。
- **不要**把"触发序列已发完"当成"保护位已关"（§1.3 的不确定点 ①）。
- **不要**在**插着多台同芯片设备**时操作（§1.3 末行）。
- **不要**把这份清单的步骤当成"已实测"——它**没有被执行过**。
